# Task 1.1. Implement the virtual dispatch benchmark

Use the Java code below as the specification for this benchmark. Port it to each language and run it on the targets listed in [targets.md](../agent-rules/targets.md).

```java
import java.util.ArrayList;
import java.util.List;
import java.util.SplittableRandom;

final class VirtualDispatch {
    interface Operation {
        int process(int value);
    }

    record AddOperation(int operand) implements Operation {
        @Override
        public int process(int value) {
            return value + operand;
        }
    }

    record MulOperation(int operand) implements Operation {
        @Override
        public int process(int value) {
            return value * operand;
        }
    }

    // Stage 1. Prepare the data outside the timed region.
    static List<Operation> prepare(int size, long seed) {
        var random = new SplittableRandom(seed);
        var operations = new ArrayList<Operation>(size);

        for (int i = 0; i < size; i++) {
            boolean add = random.nextBoolean();
            int operand = random.nextInt(1, 17);
            operations.add(add
                    ? new AddOperation(operand)
                    : new MulOperation(operand));
        }

        return operations;
    }

    // Stage 2. One timed sample containing repeats full passes.
    static long run(List<Operation> operations, int repeats, int value) {
        long checksum = 0;

        for (int n = 0; n < repeats; n++) {
            for (Operation operation : operations) {
                checksum += operation.process(value);
            }
        }

        return checksum;
    }
}
```

- Dataset generation is outside the timed region and the random-number generator is not part of this benchmark. Each implementation may use a standard random-number generator built into its language or runtime. The seed is optional. When it is omitted, use a system-generated seed. Report the effective seed used for the run. Generate operation types with equal probability and operands uniformly in the inclusive range 1 through 16. Keep the generated sequence and its order unchanged across all passes within a run.
- Match Java `int` arithmetic semantics for `Operation.process`: values and operands are signed 32-bit integers, and addition and multiplication wrap modulo 2^32 without throwing on overflow. Interpret the low 32 bits as a signed two's-complement value. Sign-extend each returned `int` value when adding it to the signed 64-bit checksum. Languages where signed overflow has different or undefined behavior must implement Java's wrapping behavior explicitly.
- Call `process` through the language's equivalent of the common `Operation` interface. Time the entire call to `run`, including both loops.
- Define one benchmark operation as one complete call to `run`. Each operation performs `operations.size() * repeats` calls to `Operation.process`.
- Use and report the checksum after timing so the result is observable. This prevents a compiler from removing the dispatch loop as unused work. Keep checksum reporting outside the timed region.
- Before retaining measurements, compare the checksum with an expected value calculated outside the timed region from the generated operations, `repeats`, and `value`. Calculate the expected value without using the timed virtual dispatch path. Reject the run if the values differ.

## Timing and execution

- Use a monotonic, high-resolution clock provided by the language or runtime.
- Time each complete call to `run`. Keep dataset preparation, expected-checksum calculation, validation, and output outside the timed region.
- Do not force, suppress, or exclude garbage collection during a timed sample. Garbage collection and other runtime activity caused by the workload are part of the result.
- Retain every successful sample, including slow samples and spikes, so warmup behavior and performance dynamics can be analyzed later. Do not discard outliers merely because they are slow.
- The benchmark does not need to determine during execution whether it has reached steady state. Write measured in-process samples with phase `unclassified`, and preserve the ordered sample series and elapsed time so later analysis can identify warmup and any stable region. Do not label a sample `steady_state` solely because it occurs after the configured warmup samples.
- Run the workload on one application thread, restrict the benchmark process to one logical CPU, and run only one benchmark target at a time. Record the machine and execution state later in the benchmark report.

## Diagnostic runs

Runtime-specific compilation and optimization logging may be enabled in separate diagnostic runs. For example, HotSpot tiered compilation logs can show whether a method reached C2 compilation level 4. Keep these logs with the run diagnostics, but do not enable verbose compilation logging during headline timing runs.

Compilation at a runtime's highest optimization tier is supporting evidence, not proof of steady-state performance. Use the timing series to assess stability and use diagnostic logs to help explain compilation, recompilation, deoptimization, garbage collection, and other observed transitions.
