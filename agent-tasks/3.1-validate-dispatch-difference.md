# Task 3.1. Validate virtual-versus-enum dispatch differences

Run matched repetitions of the virtual-dispatch benchmark from
[Task 1.1](1.1-implement-virtual-dispatch.md) and the enum-dispatch benchmark
from [Task 2.1](2.1-implement-enum-dispatch.md) for Java, C, and C++. Analyze
whether the observed within-target differences are reproducible and large
enough to support further investigation.

Follow the repository [benchmark targets](../agent-rules/targets.md),
[tooling](../agent-rules/tooling.md), [Docker](../agent-rules/docker.md),
[runner](../agent-rules/runner.md),
[project structure](../agent-rules/project-structure.md),
[report format](../agent-rules/report.md), and
[analysis](../agent-rules/analysis.md) rules.

## Motivation

The existing Task 1.x and Task 2.x timing runs used different values and sample
counts, so subtracting or dividing their reported medians does not provide a
matched virtual-versus-enum comparison. A separate experiment also suggested
that indirect calls may be expensive. This task reruns both workloads under
the same settings and checks the result independently.

This comparison does not, by itself, isolate the cost of one indirect call.
The workloads also differ in data representation, object or record layout,
iteration, optimizer decisions, and runtime devirtualization. Interpret a
timing difference as a complete-workload difference unless a matched control
isolates a mechanism.

## Docker collection instructions

Run the task collection script from the repository root. The standard scripts
use the Docker CLI, build the artifacts before measurement, pin the containers
to one logical CPU, and retain the normal clean-runtime protections. Avoid
chatting with an agent, compiling other projects, or running other substantial
host work until collection completes: unrelated host load can affect CPU
scheduling, shared caches, memory bandwidth, temperature, and turbo frequency.

Choose a new comparison ID if `dispatch-validation-001` has already been used.
The preflight checks deliberately stop rather than overwrite or append to an
existing comparison directory.

```sh
./task-scripts/3.1-collect.sh dispatch-validation-002
```

The script prints UTC timestamps and `BUILD`, `RUN`, and `DONE` progress lines
containing the progress count, trial, workload, target, and elapsed run time.
It also copies every completed run log to a filename containing its trial
number before the standard filename can be overwritten by the next trial.

If the installed `docker` command is Podman compatibility mode, preserve that
fact in the generated logs and treat the execution engine as Podman during
analysis. Do not relabel it as a Docker Engine run merely because the command
name is `docker`.

## Validation and analysis

After collection, validate all CSVs and logs before comparing results:

- Require both workloads to contain all seven targets and trials 1 through 5.
- Require 10 warmup and 30 measured samples per target and trial.
- Verify settings, checksum success, configuration, toolchain, host,
  architecture, engine, CPU control, and resource limits from the logs.
- Reject duplicate or incomplete trials and explain every exclusion.
- Keep warmup and measured samples separate. Do not silently call the source
  `unclassified` rows steady state.
- Apply one stated stability check consistently to both workloads.
- Summarize each trial first, then compare the five trial summaries. Do not
  pool 150 within-process samples as though they were independent trials.
- For each target, report both workload medians, the paired absolute
  difference, and the paired enum/virtual ratio across matching trial numbers.
  Include a spread measure and show the direction consistently.
- Compare only the same target across the two workloads. Cross-target rankings
  are secondary and must not be used to estimate dispatch overhead.
- Relate results to the existing generated-code evidence only where the
  configuration matches. In particular, distinguish retained indirect calls,
  JIT devirtualization, scalar enum branches, and SIMD enum lowering.
- State whether the difference is consistent across trials and whether the
  evidence warrants a follow-up controlled benchmark that differs only in the
  dispatch mechanism.

- The analysis uses paired trial summaries and reports absolute and relative

- Conclusions distinguish complete-workload observations from isolated
  indirect-call cost.
- The Task 3.1 row in `task-execution.md` has no applicable rule left as
