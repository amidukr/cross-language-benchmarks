## Required README content

### Project purpose and status

- Explain that the project compares equivalent workloads across languages,
  compilers, and runtimes under documented, reproducible conditions.
- State that the current implemented workloads compare virtual method dispatch
  with enum/tag-based dispatch.
- Clearly distinguish completed work (Tasks 1.x, 2.x, and 3.1) from planned
  work. If Task 4.1 is mentioned, label it as planned and do not present memory
  results.
- Link the task specifications and shared benchmark rules for readers who want
  the exact contracts.

### Workloads and targets

- Briefly define one timed operation for each workload and explain what work is
  included in the timing.
- State that the workloads are similar experiments, not source-identical
  programs and not an isolated measurement of dispatch instruction latency.
- List the 13 canonical targets and use language-first human-readable names,
  for example `Java (Eclipse Temurin, HotSpot C2) [temurin-c2]` rather than
  `Temurin` alone.
- Explain the distinction between JVM/JIT, native AOT, and conventional native
  compiler targets where needed to prevent misleading comparisons.

### Evidence map

Provide a compact table that maps each completed task or subject to:

- Its workload directory.
- Its human-readable analysis report.
- Its raw timing or diagnostic evidence directory.
- The workload README containing exact build, run, and assembly commands.

Readers must be able to navigate from the root README to Task 1.x virtual
dispatch, Task 2.x enum dispatch and vectorization diagnostics, and Task 3.1's
matched validation without searching the repository tree.

### Findings

Summarize only conclusions supported by the reports. At minimum, cover:

- The original Task 1.2 and 2.2 timing reports are single-process-trial
  observations with source measurements still classified as `unclassified`.
- Task 3.1 supplies five matched fresh-process trials for Java, C, and C++ and
  is the preferred source for virtual-versus-enum comparisons.
- Task 3.1 compares complete workloads; it does not isolate the cost of one
  indirect call because representation, traversal, optimizer decisions, and
  other work also differ.
- Generated-code evidence explains several observed differences, including
  SIMD enum lowering for Rust and C compiled with Clang in the captured
  configuration, and scalar branch-based lowering for several other targets.
- Clang's diagnostics report the C loop as profitable to vectorize and the C++
  loop as not beneficial, but the precise C++ cost-model cause remains
  unresolved. Preserve this uncertainty explicitly.
- Java results must identify Java in every target-oriented table and must
  distinguish Java (Eclipse Temurin, HotSpot C2), Java (GraalVM JIT), and Java
  (GraalVM Native Image).

Do not turn provisional rankings into general language rankings. Do not quote
an isolated median without its run scope, trial count, workload, unit, and a
link to the supporting report. Prefer a short qualitative summary and direct
readers to the report tables over duplicating every number.

### Reproducing the work

- State the Linux, Docker-compatible engine, CPU-affinity, and toolchain/image
  prerequisites accurately.
- Include a short quick-start that builds and runs one target, followed by links
  to the two workload READMEs for complete container, native, assembly, and
  vectorization-diagnostic commands.
- Explain `CONTAINER_ENGINE=podman`, the distinction between Docker mode and a
  Podman compatibility wrapper, and the requirement to keep execution modes
  separate when comparing results.
- Include the Task 3.1 collection command and its clean-host warning. Do not
  claim it is safe to reuse an existing comparison ID.
- Explain where CSVs, logs, assembly captures, manifests, and analyses are
  written.

### Interpretation and limitations

- Explain warmup versus `unclassified` samples and why the current reports do
  not silently relabel them as steady state.
- Mention language-specific random-number sequences and equivalent rather than
  byte-identical prepared data.
- State the principal limitations recorded by the reports: host-specific
  observations, incomplete runtime diagnostics or provenance where applicable,
  and the absence of a matched control that changes only dispatch.
- Point to Task 3.1's proposed controlled follow-up rather than claiming the
  dispatch mystery is solved.

## Documentation quality

- Use repository-relative Markdown links and verify every link resolves with
  exact filename case.
- Keep the README useful when viewed on a public Git host; do not use absolute
  local paths, user names, host names, container IDs, or other machine-specific
  identifiers outside a clearly attributed report summary.
- Do not duplicate raw logs or large result tables in the README.
- Do not expose credentials, tokens, private URLs, or unrelated environment
  details found in artifacts.
- Use concise headings and tables that render with standard GitHub-flavored
  Markdown.
