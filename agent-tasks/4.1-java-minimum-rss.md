# Task 4.1. Measure minimum Java application RSS

Implement and measure several minimal Java applications to determine their
process resident-set-size (RSS) footprints across Java execution modes,
garbage collectors, and heap-sizing policies. Automate startup, readiness,
representative use, memory sampling, correctness checks, and cleanup through
Docker-compatible scripts.

Follow the repository [benchmark targets](../agent-rules/targets.md),
[tooling](../agent-rules/tooling.md), [Docker](../agent-rules/docker.md),
[runner](../agent-rules/runner.md),
[project structure](../agent-rules/project-structure.md),
[report format](../agent-rules/report.md), and
[analysis](../agent-rules/analysis.md) rules where applicable. Memory-specific
requirements in this task take precedence when the timing-oriented runner
interface does not apply directly.

## Questions to answer

For each application, target, and supported garbage collector:

1. What RSS does the application reach after natural startup and an idle
   settling period with default JVM or native-image memory settings?
2. What RSS does it reach after a small representative workload and another
   idle settling period?
3. How does RSS change when the initial heap is minimized while the maximum
   heap remains at its default?
4. What is the smallest maximum heap that still starts, becomes ready,
   completes the correctness workload, and remains alive without an
   `OutOfMemoryError`?
5. How do a small initial heap, a constrained maximum heap, and a fixed heap
   (`-Xms` equal to `-Xmx`) differ?
6. Which collectors and heap options are actually supported by each target?

Do not equate heap size with RSS. RSS also includes committed heap pages,
metaspace, code cache, JIT/compiler data, thread stacks, garbage-collector
metadata, native libraries, direct buffers, and other native allocations.
`-Xmx` limits Java heap size; it is not a process-memory limit.

## Applications

Create a new workload at `java-memory-test/` containing four applications.
All applications must emit a machine-readable readiness marker and remain
alive until the measurement controller terminates them.

| Application ID | Required behavior |
| --- | --- |
| `console` | A dependency-free Java application that retains the string `Hello World`, prints it once to standard output, emits readiness, and then blocks without a busy loop. It must not exit immediately because its steady RSS must be sampled. |
| `swing` | A dependency-free Swing application with one visible `JFrame` containing one `JLabel` whose text is exactly `Hello World`. Emit readiness from the event-dispatch thread only after the frame is visible. Run under a pinned Xvfb image/configuration. Measure the Java process separately from Xvfb, and also record total container memory. |
| `spring-boot` | A minimal Spring Boot 4.1.2 HTTP application with one controller at `GET /hello-world`, returning status 200, content type `text/plain`, and body exactly `Hello World`. Disable optional features only through documented application configuration, and record every change. |
| `quarkus` | A minimal Quarkus 3.40.1.1 LTS HTTP application with one resource at `GET /hello-world`, returning status 200, content type `text/plain`, and body exactly `Hello World`. Disable optional features only through documented application configuration, and record every change. |

Pin framework, plugin, Maven, base-image, OS-package, Xvfb, JDK, and GraalVM
versions. Commit Maven wrapper metadata and dependency locks or resolved
dependency manifests sufficient to reproduce the builds. Do not add actuator,
management, JSON, template, database, logging bridge, or other application
features that are not needed for the endpoint.

## Targets

Use only the existing Java target identities:

| Target | Execution modes |
| --- | --- |
| Java (Eclipse Temurin, HotSpot C2) [`temurin-c2`] | JVM |
| Java (GraalVM JIT) [`graalvm-jit`] | JVM with the Graal top-tier compiler enabled by the distribution defaults |
| Java (GraalVM Native Image) [`graalvm-native`] | Native executable |

Reuse one application source per framework across the Java targets. Attempt
all four applications for all three target identities. If Swing or a framework
cannot be built as a native image, preserve the failed build log and record
the target/application combination as unsupported rather than silently
omitting it or substituting a different program.

## Garbage-collector discovery

“All collectors” means all collectors that the exact pinned runtime or
native-image distribution accepts for the application and platform. Probe
support before collecting measurements and retain the command, version,
output, exit status, and selected collector. Do not infer support merely from
a generic documentation list.

For both JVM targets, attempt at least these configurations:

| Collector ID | JVM selection option |
| --- | --- |
| `default` | No collector-selection option; record the ergonomically selected collector |
| `serial` | `-XX:+UseSerialGC` |
| `parallel` | `-XX:+UseParallelGC` |
| `g1` | `-XX:+UseG1GC` |
| `zgc` | `-XX:+UseZGC` |
| `shenandoah` | `-XX:+UseShenandoahGC` when the distribution provides it |
| `epsilon` | `-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC` when provided |

For Native Image, attempt separate build artifacts for `serial`, `epsilon`,
and `G1` using `--gc=<collector>`. Serial is the expected default. G1 may be
unavailable in the installed GraalVM edition, and that outcome must be recorded
as unsupported. Native-image GC choice is a build configuration, whereas JVM
GC choice is a runtime configuration; do not combine their results as though
they were selected at the same stage.

Epsilon does not reclaim memory. Treat successful completion as valid only if
the application completes the defined workload without exhausting its heap.
Do not generalize an Epsilon result to a long-running service.

## Heap-setting experiment

Run this staged matrix independently for every supported
application/target/collector combination. Record both requested and effective
heap values; a runtime may round or reject small values.

### 1. Default

Run without `-Xms`, `-Xmx`, `InitialRAMPercentage`, `MaxRAMPercentage`, or
equivalent heap-sizing overrides. Record effective initial and maximum heap
sizes from the runtime.

### 2. Minimize the initial heap only

Keep the maximum heap at its default. Probe `-Xms` values in this ordered grid:

```text
1m, 2m, 4m, 8m, 12m, 16m, 24m, 32m, 48m, 64m
```

Stop only after identifying the smallest accepted value that passes the full
viability test. Record rejected values and runtime rounding. Compare it with
the no-`-Xms` default; a smaller requested initial heap does not automatically
mean lower RSS.

### 3. Minimize the maximum heap only

Leave the initial heap unspecified and probe `-Xmx` using this grid, starting
from a known-successful high value and descending:

```text
512m, 384m, 256m, 192m, 128m, 96m, 64m, 48m, 32m, 24m, 16m, 12m, 8m, 4m
```

Identify the smallest value that passes. Do not classify a process that starts
but fails readiness or requests as viable.

### 4. Combined minimum

Run with the smallest accepted `-Xms` from stage 2 and the smallest viable
`-Xmx` from stage 3. If that combination fails, increase values through the
same grids until the smallest viable pair is found.

### 5. Fixed heap

Set `-Xms` equal to `-Xmx` at the smallest viable maximum from stage 3. This is
a separate footprint policy, not an expected memory optimization.

For Native Image, use only runtime heap options supported by the exact built
artifact and record rejected options. Native-image build-time defaults and
runtime overrides must remain distinct in configuration IDs.

## Viability and application exercise

A configuration is viable only when all required checks pass:

- The process starts without option errors or `OutOfMemoryError`.
- It emits the expected readiness marker within 120 seconds.
- The console and Swing processes remain responsive and alive for the entire
  measurement interval.
- The Swing frame reaches its ready state under Xvfb.
- Each REST application returns the exact expected status, content type, and
  body for 1,000 sequential requests with no failures.
- The process remains alive for the final settling and measurement window.
- Shutdown completes after `SIGTERM`; use `SIGKILL` only after a documented
  timeout.

Do not call `System.gc()`, `jcmd GC.run`, or an equivalent forced collection in
the headline configuration. A forced-GC experiment may be recorded separately
with a distinct configuration ID, because it answers a different question.

## Automated memory collection

Implement Docker-compatible orchestration that performs these steps without
manual observation:

1. Start one clean container and one application process for one trial.
2. Record container ID, image identity, application PID, process start time,
   target, collector, requested/effective heap settings, CPU limit, memory
   limit, architecture, kernel, and toolchain.
3. Poll the readiness marker, Swing state, or REST endpoint until ready or the
   timeout expires.
4. Sample natural post-readiness idle memory for 30 seconds at 100 ms intervals.
5. For REST, issue 1,000 sequential correctness requests. For console and
   Swing, perform only their defined readiness/liveness checks so artificial
   allocation is not introduced.
6. Allow a 10-second quiescence period without forced GC.
7. Sample post-exercise idle memory for 30 seconds at 100 ms intervals.
8. Stop the application, preserve stdout/stderr and GC logs, and record its
   exit outcome.

The primary process RSS source is `/proc/<application-pid>/smaps_rollup` field
`Rss`. Use `/proc/<pid>/status` `VmRSS` only as a recorded fallback. Also
capture `VmHWM` or an equivalent process peak and the container cgroup's
`memory.current` at every sample. The process RSS excludes Xvfb; cgroup memory
includes all processes and container overhead. Label them distinctly.

Do not use `docker stats` rounded display values as the only evidence. The
sampler must retain raw byte values and monotonic timestamps. Confirm that PID
reuse cannot cause samples from another process.

Fix resource controls for comparability. Use one logical CPU and a 1 GiB
container memory limit unless preliminary viability requires a documented
larger limit. The fixed container limit is important because default JVM and
native-image heap ergonomics depend on visible memory.

Run five fresh-container trials for every retained configuration. Run
configurations sequentially. Do not run multiple measured application
containers concurrently, and avoid other substantial host work during
collection.

## Metrics and output

Store raw evidence beneath:

```text
reports/java-memory-test/<run-id>/
  <application-id>/<target-id>/<collector-id>/<heap-profile>/<trial>/
```

For each sample retain at least:

- Monotonic time from readiness in nanoseconds.
- Phase: `startup`, `ready-idle`, `exercise`, `post-exercise-idle`, or
  `shutdown`.
- Process RSS in bytes.
- Process high-water RSS in bytes when available.
- Cgroup memory in bytes.
- Java heap used, committed, initial, and maximum bytes when available through
  a nonintrusive runtime endpoint or recorded diagnostic interface.

Define task-specific CSV metrics before emitting them. At minimum include
`rss_bytes`, `cgroup_memory_bytes`, `peak_rss_bytes`, and `readiness_time_ms`.
Do not store only a precomputed minimum; preserve the ordered sample series.

For every trial and phase, derive:

- Minimum observed RSS, which directly answers the requested minimum but is
  sensitive to sampling noise.
- 10th-percentile, median, and maximum RSS.
- RSS range and final-window stability.
- Peak RSS over the complete process lifetime.
- The same summaries for cgroup memory.

Treat the phase median and 10th percentile as the primary stable-footprint
statistics. Report the absolute minimum as a secondary statistic so one
transient sample is not mistaken for a sustained footprint.

## Required scripts

Provide executable scripts under `java-memory-test/` for:

- Building all application/target/collector artifacts.
- Probing supported collectors and heap options.
- Running one explicit configuration and trial.
- Running the staged matrix sequentially with visible progress containing the
  application, target, collector, heap profile, candidate value, and trial.
- Validating raw samples, readiness, request results, exit status, and required
  provenance.
- Summarizing valid trials without deleting failures or slow/high-memory
  samples.

Scripts must support Docker and Podman through `CONTAINER_ENGINE`, fail clearly
on invalid arguments, and never overwrite a previous run ID. Preserve a
manifest for unsupported and failed configurations.

## Analysis

The analysis must:

- Compare applications only within matched target, collector, heap policy,
  resource limit, host, engine, and measurement phase.
- Present JVM and Native Image configurations separately.
- Report all five trial summaries before aggregating them.
- Identify unsupported collectors and failed minimum-heap candidates.
- Show the difference between default RSS, minimum-initial-heap RSS,
  minimum-maximum-heap RSS, combined-minimum RSS, and fixed-heap RSS.
- Distinguish process RSS, container memory, Java heap, and peak RSS.
- State startup/readiness and request correctness alongside memory results so
  a nonfunctional low-memory configuration cannot appear successful.
- Avoid claiming that the smallest successful grid point is a universal lower
  bound; it is the smallest value tested under this workload and environment.
