# Task 4.2. Analyze Java application RSS results

Analyze the completed memory measurements collected for
[Task 4.1](4.1-java-minimum-rss.md). Produce tables that make application,
runtime mode, garbage collector, and `-Xms`/`-Xmx` effects easy to compare.

Follow the repository [benchmark targets](../agent-rules/targets.md),
[project structure](../agent-rules/project-structure.md),
[report format](../agent-rules/report.md), and
[analysis](../agent-rules/analysis.md) rules where applicable. Read the
Task 4.1 memory-specific metrics and interpretation requirements as well.

## Inputs and validation

- Analyze only completed run IDs with a final `status=complete` matrix
  manifest. Do not read or summarize a run while it is still running.
- Include `memory-002` and any later run, such as `memory-003`, only if its
  collection has completed when analysis begins. List every included run ID
  and source summary/CSV in the report.
- Validate each trial manifest, `results.csv`, and `raw-samples.csv` against
  the run configuration. Check readiness, process outcome, REST correctness,
  sample count, phase, effective heap settings, selected collector, runtime,
  host, container engine, resource controls, and failure reason.
- Preserve failed and unsupported configurations in the tables using clear
  status text. Do not present their RSS as a successful viable measurement.
- Keep survey and full-duration measurements separate. For full trials, keep
  `ready-idle` and `post-exercise-idle` phases separate. Do not combine JVM
  runtime-selected collectors with Native Image build-time collectors.

## Required tables

Use the 10-second `survey-idle` phase for the primary five-profile matrix.
Use the per-trial median RSS in MiB as the table's primary value. Preserve
trial identity: if a configuration has more than one trial, show a separate
row for each run ID and trial rather than pooling individual samples or
silently averaging trials. When every included configuration has one trial,
omit the redundant run/trial table column and identify the run in the table
introduction. State the number of raw samples represented by each value.
Include the P10 and relevant range/peak findings in the report's
interpretation so the median is not mistaken for the entire RSS distribution.

### Cross-application summary

Create one summary table with one row per execution target and collector, plus
run/trial identity only when multiple trials are present. Include the execution
kind explicitly as JVM or Native Image AOT.
Use separate application columns for Console, Swing, Spring Boot, and
Quarkus. Each cell contains that application's median process RSS in MiB for
the default heap profile, or an explicit failure/unsupported/no-result
status.

### Heap-profile tables by application

Create a separate table for each of Console, Swing, Spring Boot, and Quarkus.
Rows identify execution kind and target, and selected/build collector. Include
run/trial in rows only when multiple trials are present. Columns represent the
five exact `-Xms`/`-Xmx` combinations from Task 4.1:

| `-Xms`  | `-Xmx`   |
| ------- | -------- |
| default | default  |
| 1 MiB   | default  |
| 1 MiB   | 16 MiB   |
| 1 MiB   | 1024 MiB |
| 512 MiB | 1024 MiB |

Cells contain median RSS in MiB for the trial, with the sample count. Use
explicit status text for failed, unsupported, missing, or incomplete
configurations; do not substitute zero or treat unsupported configurations as
failures. Include only configurations supported by evidence.

## Comparison and interpretation

- Compare application types within matched target, collector, heap profile,
  measurement phase, host, engine, resource limits, and run conditions.
- Describe how changing `-Xms` and `-Xmx` changes process RSS separately for
  each application. Distinguish heap reservation/commitment from process RSS
  and cgroup memory.
- Report JVM collector selection as runtime configuration and Native Image GC
  as build configuration. Keep their results distinct.
- Treat one-trial results as an initial observation, not independent
  replication. Do not infer a universal minimum viable heap from the tested
  profiles.
- Explain the OOM and failed-readiness cases, including Spring Boot with Java
  (GraalVM Native Image), Epsilon, and `-Xms1m -Xmx16m` when present in the
  included completed run. Preserve the log-supported reason and exclude the
  failed configuration from viable RSS comparisons.
- State limitations from missing or failed configurations and avoid claims
  beyond the recorded workload, runtime, collector, host, and sample phase.

## Outputs

- Write the analysis to [`reports/java-memory-test.md`](../reports/java-memory-test.md).
- Update the Java RSS chapter in the root [`README.md`](../README.md) with a
  concise summary of the completed results and a link to the analysis.
- End the analysis with a `Code under test` section containing the relevant
  source examples for the measured Console, Swing, Spring Boot, and Quarkus
  Java applications, with source paths.
- Preserve all original run evidence. Do not add generated data or other files
  under `agent-tasks/` beyond this task specification and
  `task-execution.md`.

- All included runs and trials have been validated, with every failed or
  unsupported combination accounted for.
- The report contains the cross-application summary table and four
  application-specific `-Xms`/`-Xmx` tables with runtime/collector identity,
  applicable trial context, units, and statuses.
- Survey, full-duration, and measurement phases are kept separate.
- The report explains the memory-setting effects, OOM/viability results, and
  limits on comparison.
- The report ends with source-linked code examples for the four Java apps.
- The root README contains a concise results summary and analysis reference.
- The Task 4.2 row in `task-execution.md` has no applicable rule left as
  `to be done`.
